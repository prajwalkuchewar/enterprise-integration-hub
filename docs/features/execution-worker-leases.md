# Execution worker ownership leases

The execution dispatch inbox has a SQL Server lease primitive for a future execution worker. `ClaimAsync` atomically claims one eligible inbox entry using row locks and returns a unique token. Expired claims can be reclaimed. `RenewAsync`, `ReleaseAsync`, and `CompleteAsync` only succeed while that token still owns an unexpired lease. SQL Server's clock determines lease expiry and claim eligibility, avoiding differences between worker clocks.

Release may set an availability time for future scheduling. Completion also requires the associated execution to be in a terminal state. The migration leaves existing inbox entries available for claiming. Lease durations are specified in whole seconds and must be between 1 and 86400.

This is not a running execution worker. The worker must renew or cancel long-running work safely and ensure the lease remains valid before starting an external call. A lease does not by itself prevent an external destination from processing a request after a lease expires or a network failure becomes ambiguous. The logical step ID is a stable idempotency key across attempts, but destination support is required and exactly-once side effects cannot be guaranteed.

Attempt creation and outcome changes are routed through the execution aggregate: steps run in order, successful steps cannot be restarted, and a scheduled retry cannot start before its due time. The attempt repository locks and checks the inbox lease in the same SQL transaction as each state change. It rechecks expiry before commit, persists a running attempt before returning work, and records the result and inbox transition atomically. A replacement owner records the prior in-flight attempt as interrupted before retrying it, subject to the supplied attempt limit. Existing receipts without payloads are failed explicitly instead of being sent.

Attempt work includes sensitive event data and must not be logged or serialized into diagnostics. Failure diagnostics use fixed messages rather than raw destination content.

The execution orchestrator claims and renews leases, starts ordered attempts, invokes a supplied destination implementation outside the database transaction, and records each outcome. It applies capped exponential backoff with jitter; the repository calculates the persisted retry deadline using SQL Server time. The hosted worker is disabled by default. To enable automatic delivery, configure `Outbox:Enabled`, `Kafka:ConsumerEnabled` and `ExecutionWorker:Enabled`, the broker and a non-empty `DestinationHttp:AllowedOrigins` list, and credentials for each destination. Apply the database migrations through the normal deployment process before enabling the worker; migrations are not applied automatically. Replay and a dead-letter operator experience remain unimplemented.

The initial REST contract sends the accepted JSON payload as a POST, with the logical step ID in `Idempotency-Key` and an optional `X-Correlation-ID`. Connector-specific HTTP methods, SOAP, GraphQL and SFTP delivery are not implemented. HTTP 2xx succeeds; 408, 429, 5xx, network failures and timeouts are transient; other responses are permanent failures. Redirects are not followed. Each completed attempt can store the HTTP status and elapsed milliseconds, but not the response body or headers. Existing rows have null diagnostics.

`DestinationHttp:AllowedOrigins` is an explicit list of exact HTTPS origins (scheme, hostname and port); empty means no destination is permitted. URLs with user information, query strings or fragments are rejected. Proxy use, cookies and automatic redirects are disabled. DNS answers are checked for public addresses and the validated address is used for the actual socket, preventing a second DNS lookup from bypassing the policy. Private, loopback, link-local, reserved and other special-use addresses are blocked. For local tests only, `DestinationHttp:AllowInsecureHttp` and `DestinationHttp:AllowLoopback` may be enabled in the Development or Testing environment. Loopback additionally requires a literal IP address in the exact allowed origin; DNS names resolving to loopback are rejected. These flags are rejected in other environments. Private network destinations are not currently supported.

Credentials are resolved at invocation time from the application's configuration providers under `DestinationCredentials:<connector-guid>`. API-key connectors require `HeaderName` (an `X-` header) and `ApiKey`; Basic connectors require `Username` and `Password`; Bearer and OAuth2 connectors require `AccessToken`. OAuth2 currently uses an externally provisioned access token: token acquisition and refresh are not implemented. Configure secrets through a secure external provider or environment variables, not source-controlled settings. Environment variables alone are not a full secret-management solution; access, rotation and production secret-provider integration remain operator responsibilities. Missing or invalid credentials fail the attempt without exposing the credential. Never log the payload, credential configuration or raw destination response.

SQL Server integration tests cover concurrent claims (including read-committed snapshot isolation), expiry and reclaim, stale-token fencing, delayed release, renewal, ordered attempts, interrupted-attempt recovery, missing payloads, and transaction rollback.

The opt-in end-to-end test uses an isolated SQL database, a Kafka topic and a loopback HTTP server. Set `EIH_SQLSERVER_TEST_CONNECTION` and `EIH_KAFKA_TEST_BOOTSTRAP` to run it. It verifies authenticated ingestion and duplicate handling through the outbox, broker, inbox and hosted worker, including a retry, ordered delivery, a stopped worker's interrupted attempt and recovery after lease expiry. The test simulates lease expiry in its isolated database rather than waiting for the production lease duration.
